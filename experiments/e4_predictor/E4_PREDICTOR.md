# E4 — Predictor Upgrade and Confidence Calibration

Source spec: `Experiments.md` §"E4 — Predictor upgrade and confidence calibration [P1]".
This file is the design note: what's implemented, what it assumes, a real bug found while
building it, how to run/interpret it. **Results go in `RESULTS.md`, auto-generated by
`train_eval.py` on every run — don't hand-edit it.**

**This experiment runs on a laptop, not (only) the GPU server.** Experiments.md says so
itself — "trains in minutes on CPU/MPS" — and that's confirmed true here: the full
sweep (both models, 3 ablation variants, recall-vs-bytes curve, calibration, cross-domain
transfer) ran end-to-end on this machine's CPU (no CUDA at all) in under 6 minutes. The
same command (`run_e4.sh`) works unmodified on the GPU server; it just won't be any
faster there for this particular workload (see `--device` below).

## Why this experiment exists

The pilot's frequency-table predictor gets 55-62% recall at m=2k. Two things have to
improve for router-guided prefetch to be worth anything, given E1's own finding that
m is a bandwidth multiplier (fetching 2k candidates to catch k needed ones is a 2x byte
tax): higher recall at **lower** m, and **calibrated** per-expert confidence, because
E7's precision-gating decides how many bytes to spend on each candidate based on exactly
how sure the predictor is about it. An uncalibrated confidence score is decoration; a
calibrated one is an input to a real decision.

## What's actually implemented

| Experiments.md E4 step | File / function | Notes |
|---|---|---|
| 1. Predictor v2 (small MLP, per-layer, trained per model) | `mlp.py::TinyMLP`, `train_predictor` | Per-expert sigmoid outputs (BCEWithLogitsLoss), not a softmax over "the" next expert — this is what makes `sigmoid(logit)` a genuine per-candidate probability, the exact quantity E7's `τ_lo`/`τ_hi` thresholds need. One MLP per (model, d, layer), matching the pilot's own per-layer transition table so the comparison in step 2 is apples-to-apples. |
| 2. Ablate the input: ids / +gate weights / +router entropy / +hidden state | `features.py::build_layer_dataset`, variant ∈ `VARIANTS` | (a)-(c) come straight from fields `collect.py` already logs (`topk`, `gate_w`, `router_entropy`) — no new GPU collection needed. (d) needs `collect_hidden_states.py`'s output (GPU-only, optional); skipped with an explicit message, not silently dropped, when absent. |
| 3. Recall-vs-bytes curve | `train_eval.py::recall_vs_bytes` | Reuses the winning variant's already-trained models' cached logits — no retraining per m. `bytes_per_layer = m * expert_bytes(precision)`, i.e. the literal cost of fetching m non-resident candidates; doesn't apply a residency discount (that's what the "nonresident" recall definition already isolates). |
| 4. Calibration (ECE, reliability diagram, temperature scaling) | `calibration.py` | Guo et al., ICML 2017. Calibrated over flattened (row, candidate-expert) pairs — the same granularity E7 would query at decision time — not just "was the top-1 guess right." |
| 5. Cross-domain transfer | `train_eval.py::cross_domain_transfer` | Fits on ALL of one domain's requests (not the standard within-domain 70/30 split), tests on the other, both directions, using the winning variant at d=1. |

## A real bug found while building this (feature-scale collapse)

The first full run produced results that looked like a genuine, interesting finding:
adding gate weights (`ids_gate`) and router entropy (`ids_gate_entropy`) made recall
**collapse** from 42% (`ids` alone) to 0.7% and 0.1% respectively — as if giving the
predictor *more* information made it catastrophically worse. That's not a plausible
scientific result (more information should never hurt this badly), so before writing it
into a report as a "finding," it got diagnosed rather than trusted.

Diagnosis (`experiments/e4_predictor/` — reproduced with a one-off script, not committed):
training the same MLP on both variants for the same 60 epochs at the same learning rate
and comparing loss curves showed `ids_gate` simply hadn't converged as far — because its
input values are **10-60x smaller in magnitude** than `ids`'s clean 0/1 encoding
(`ids` column mean 0.125, `ids_gate` column mean 0.011, `router_entropy` on top of that
sits on a totally different nats-scale, 0 to ln(n_experts) ≈ 4.16). Same optimizer,
same step budget, much smaller effective gradient signal per step ⇒ the network hadn't
finished learning within the fixed epoch count. This is a **feature-scaling bug**, not a
finding about where predictive signal lives.

Fix: `mlp.py::standardize_train_test` — z-score every feature column using TRAIN-set
mean/std (never test-set statistics, to avoid leakage), applied before training and
before inference. Verified on a single real layer that this brings all three variants to
comparable, monotonically-non-decreasing recall (more information now helps or is
neutral, never catastrophically hurts) within the same epoch budget. The committed
`RESULTS.md` reflects the standardized numbers; a regression test
(`test_small_scale_features_do_not_collapse_recall_vs_large_scale_features_when_standardized`)
locks in the fix on synthetic data so this class of bug can't silently reappear.

**Lesson for anyone extending this**: any new feature added to a variant (E5's
lookahead depth reuses these same modules) needs to go through standardization too —
`train_eval.py`'s two training call-sites both do this already; a new call-site that
skips it will silently reproduce this exact bug.

## Other honest design decisions

- **One MLP per (model, d, layer)**, not one shared model across layers. Matches the
  pilot's own per-layer transition table's granularity, and avoids conflating a
  layer-index confound with the actual input-feature ablation being tested.
- **Hidden dim = 512** (not tuned): Experiments.md suggests "~0.5-2M params" as a rough
  guideline. Without the hidden-state feature, actual param counts land well under that
  (66K for OLMoE, 8.7K for Mixtral, both counts reported in `RESULTS.md` for every row) —
  a deliberately smaller net than the illustrative range, because the classification task
  (predicting up to `n_experts` sparse binary outputs from a <=200-dim input, on 30-50K
  training rows per layer) doesn't obviously need millions of parameters, and a bigger
  net risks overfitting the effective sample size rather than helping. This is a
  documented choice, not an attempt to hit an arbitrary target.
- **Temperature is fit and evaluated on the same held-out split** (no third
  calibration-only carve-out was made). `RESULTS.md` calls this out explicitly wherever
  the after-scaling ECE is reported — treat it as a mild upper bound on how much
  calibration helps, not a final number.
- **`ids_gate_entropy` is the fixed variant used for cross-domain transfer**, regardless
  of which variant won the same-domain ablation — this keeps the cross-domain numbers
  comparable across models/runs without depending on which variant happened to win.
- **Ablation (d) requires a separate GPU-only collection pass**
  (`collect_hidden_states.py`), not a `collect.py` flag — hidden states are ~100-1000x
  more bytes per record than everything `collect.py` currently logs combined; re-running
  the full 250-request workload through a hidden-state hook would produce tens of GB.
  `collect_hidden_states.py` instead subsamples (`--n-requests`, default 40) and saves a
  compact `.pt` file. Not run here (no GPU); `features.py` raises
  `MissingHiddenStateError` and `train_eval.py` skips the ablation with an explicit
  message rather than crashing or silently omitting it.

## How to run

```bash
# laptop or server, identical command:
bash experiments/e4_predictor/run_e4.sh

# once collect_hidden_states.py has produced real data on the GPU server:
bash experiments/e4_predictor/run_e4.sh  # with:
HIDDEN_STATE_FILE="olmoe=out/hidden_states_olmoe.pt,mixtral=out/hidden_states_mixtral.pt" \
  bash experiments/e4_predictor/run_e4.sh
```

## Exit criteria (Experiments.md's own wording)

> "Either recall@m=k improved >=8pp over the frequency table (⇒ MLP earns its place), or
> it did not (⇒ report the negative result, keep the frequency table, and note that the
> router's selected set already carries nearly all the available signal — also a clean
> finding)."

`train_eval.py` computes this automatically per model (see `RESULTS.md`'s "Exit
criteria" section) — both outcomes are reported as first-class results, not just the
positive one.

## What to look at after running

1. `RESULTS.md`'s ablation table for each model — does the winning variant differ
   between OLMoE (fine-grained, 64 experts) and Mixtral (coarse-grained, 8 experts)? An
   initial run found OLMoE clears the 8pp bar comfortably (+31.9pp) while Mixtral sits
   right at the boundary (+7.7pp, a negative result by the stated criterion) — worth a
   sentence in the report either way this lands on a re-run.
2. The recall-vs-bytes curve, cross-referenced against E1's roofline: at the m value E1's
   provisioning table says is affordable for a given (residency, bandwidth), what recall
   does the winning variant actually deliver?
3. The reliability diagram and ECE before/after temperature scaling — is this predictor
   already well-calibrated out of the box (small ECE, T≈1), or does scaling meaningfully
   help? That's a direct input to how much E7's precision-gating stands to gain from
   calibration specifically vs. just using raw sigmoid outputs.
4. Cross-domain transfer recall vs. same-domain — a small drop means the predictor
   learned router/model structure; a large one means it partly memorized dataset quirks.
