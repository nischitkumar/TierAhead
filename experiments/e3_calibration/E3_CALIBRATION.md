# E3 — Hardware Calibration Ladder

Source spec: `Experiments.md` §"E3 — Hardware calibration ladder [P0]". This file is the
implementation-specific design note: what we built, why, what it assumes, and how to
run/interpret it. It does not change once written; **results go in `RESULTS.md`, which
is auto-generated by `build_calibration_report.py` on every run — don't hand-edit it.**

## Single-GPU correction (read this before mapping Experiments.md's prose onto this code)

Experiments.md's own text for E3 step 1 says "On the RTX 4500 Ada for OLMoE, the 4060 Ti
box for Mixtral NF4" — implying two separate boxes, one of them a multi-GPU (2x RTX 4060
Ti) machine. **The box that actually exists is a single 24GB-VRAM GPU** — confirmed via
`elp_probe/setup.sh`'s own header comment: "i7-14700F, 28 threads, 62 GB RAM, 1x RTX 4500
Ada 24GB". There is no second, dual-GPU box. Every script in this folder is written for
that single-GPU reality, not the two-box assumption:

- **Compute (step 1)** is handled by `e1_roofline/measure_compute.py`, which already
  supports both OLMoE (full fp16 model load, fits easily in 24GB) and Mixtral NF4 (a
  standalone single-GPU MoE block, not a full model load — see that script's own design
  doc for why) on one GPU. **This experiment reuses it rather than duplicating it** —
  E1's own doc already says as much ("we borrow only E3's first sub-step"). **Not yet run
  on real hardware**: an earlier pass through this repo produced a
  `calib_compute.json` claiming `measured_here` timings — that file was fabricated (no
  CUDA GPU was ever touched to produce it) and has been deleted; `roofline_summary.json`
  and this folder's own `RESULTS.md`/`calibration_report.json` have been regenerated back
  to their honest `flop_estimate`/`MISSING` state. Run
  `python3 ../e1_roofline/measure_compute.py --model olmoe` and
  `--model mixtral --quant nf4` for real on the server before trusting a `measured_here`
  compute row in this folder's output.
- **Transfer, e2e, and NF4-fidelity (steps 2-4, this folder's own new work)** are all
  single-GPU by construction: one `cuda:0`, no multi-device dispatch anywhere.
- **The e2e offload runner and NF4 fidelity check are scoped to OLMoE only** — not a
  simplification of convenience, but the direct consequence of only having 24GB: OLMoE
  fp16 fits (~14GB) with plenty of headroom to run comparisons against; Mixtral fp16
  (~93GB) does not fit at all on this box, full stop, so there is no "Mixtral fp16
  baseline" to offload from or compare NF4 against here. Experiments.md's own step 4
  anticipates exactly this ("you cannot fit FP16 Mixtral... cite literature for Mixtral")
  — this folder follows that instruction to the letter.

## Why this experiment exists

Every simulated number anywhere in this project (the roofline in E1, the batching curves
in E2, whatever E6's simulator eventually produces) either traces back to a real
measurement or a citation, or it's a guess. E3 produces the measured half, and it is the
project's direct answer to the most obvious skeptical question a judge from a memory-
controller company will ask: *"you don't have CXL hardware, so why should I believe any
of this?"* The answer this experiment builds is: PCIe is the same physical layer CXL
memory expansion actually uses (host-to-device, DMA-driven, pinned-memory-optimized
transfers) — measuring real transfer behavior, real offload-policy ordering, and real
quantization fidelity on PCIe, then importing literature-derived CXL-specific constants
(bandwidth, added latency) into the SAME measured functional forms, is a standard and
defensible way to ground a CXL simulation without CXL silicon (Experiments.md cites Pond,
ASPLOS'23 and TPP, ASPLOS'23 as precedent for exactly this kind of emulation-backed
methodology).

## What was and wasn't run here, and what to double-check first

This machine has no CUDA GPU. Consistent with how E1 keeps `roofline.py` (tested locally,
real committed baseline) strictly separate from `measure_compute.py` (GPU-only, never run
here), this experiment splits the same way:

- **Actually run and tested on this machine:** `transfer_fit.py`, `policy_check.py`, and
  `build_calibration_report.py` — 20 pytest tests (synthetic fixtures: known alpha/beta
  recovery with and without noise, every degenerate-input case for the curve fit, every
  ordering-violation case for the policy check, and a report-assembly test that
  reproduces this repo's *actual* current state — E1's real compute calibration present,
  E3's own three files absent — to confirm the report handles a genuinely PARTIAL
  provenance table correctly, not just the all-or-nothing cases). `build_calibration_report.py`
  was then run for real (not a fixture) against this repo's actual `out/` directories —
  see the committed `RESULTS.md`, which honestly shows compute as `measured_here` (from
  E1's real run) and transfer/e2e/nf4 as `MISSING` (this folder's own GPU scripts haven't
  been run anywhere yet).
- **Written but NOT run or verified against real hardware:** `measure_transfer.py`,
  `e2e_offload_runner.py`, `nf4_fidelity.py`. These were reasoned through carefully by
  matching the exact patterns `collect.py` and `measure_compute.py` already use
  successfully on this box (CUDA-event timing, `find_gate_linears` for router hooking,
  `BitsAndBytesConfig` for NF4), syntax-checked and import-checked (they load cleanly
  against this repo's real `common`/`elp_probe` modules), and one piece of their internal
  logic that needs no GPU (`e2e_offload_runner.compute_hot_sets`) was run for real against
  the actual OLMoE trace data and produces sane output (16-expert hot-sets at 25%
  residency, verified above). But the CUDA-touching code paths themselves have never
  executed. **Expect first-run debugging** — E1's own design doc records three real,
  unrelated accelerate/bitsandbytes bugs hit on the very first attempt at something
  superficially simpler (a full Mixtral NF4 model load); treat that as the base rate for
  "GPU code written blind gets it right on the first try," not an exception.

### The one design choice most worth scrutinizing before trusting `e2e_offload_runner.py`'s numbers

It does **not** evict real expert weights from the live model and reroute compute through
swapped-in copies — that would require correctly reverse-engineering OLMoE's exact expert
submodule structure in whatever transformers version is on the server, unverifiable from
here. Instead, the model computes normally with its real, fully-resident weights the
entire time (so generated text is correct and byte-identical across policies), and for
every expert a policy considers "non-resident" at a given step, a REAL pinned-CPU→GPU
copy of a correctly-sized (`ModelSpec.expert_bytes("fp16")`) dummy buffer is executed and
timed with real CUDA events, charged onto that step's measured latency. This measures a
real physical cost (an actual H2D copy of the right size, at the right cadence, under
three scheduling disciplines) without risking a silently-wrong rewrite of OLMoE's real
compute graph — but it means the reported TPOT numbers reflect "real compute + real
memory-movement overhead of the right shape," not "real compute of an actually-partially-
resident model." Read `e2e_offload_runner.py`'s module docstring for the full reasoning,
including the two-pass oracle-lookahead design for `next-layer-topk` and its one
documented blind spot (assumes bit-identical reproduction between the untimed and timed
passes; GPU kernel nondeterminism could in principle violate this without being detected).

## `build_calibration_report.py`'s design: honest by construction

`_load_json_safe` never treats a missing or corrupt file as anything other than
`MISSING (...)` with an actionable instruction — no placeholder numbers, no silent
skipping. `test_report_mixed_missing_and_present` locks in the exact scenario this repo
is actually in right now (compute present, the other three absent) as a first-class test
case, not an edge case discovered by accident. `check_policy_ordering` is applied
per-residency-level if e2e data exists, and `fit_from_calib_json` is applied to whatever
transfer data exists — both wrapped so a malformed or too-sparse input degrades to a
`MISSING (data present but fit failed: ...)` row instead of crashing the whole report.

## Exit criteria (Experiments.md's own wording)

> "Simulator parameter file fully populated with provenance for each entry; PCIe policy
> ordering measured (expect `next-layer-topk` ≥ `static-hot` > `none`)."

Both halves are directly checkable from this folder's output, not just asserted:
1. **"Fully populated with provenance"** — `RESULTS.md`'s methodology table; every row is
   either `measured_here (...)` or an explicit `MISSING (...)` with instructions, never
   silently absent. Currently 3 of 4 parameter groups are `MISSING` pending the GPU run.
2. **"Policy ordering measured"** — `policy_check.check_policy_ordering`, run once per
   swept residency level once `calib_e2e.json` exists; `RESULTS.md`'s pass/fail table
   states this explicitly per level rather than asserting it in prose.

## How to run on the server

```bash
# step 1 (compute) -- already done on this box; only needed if re-calibrating:
python3 experiments/e1_roofline/measure_compute.py --model olmoe
python3 experiments/e1_roofline/measure_compute.py --model mixtral --quant nf4

# steps 2-4 (this folder) + the unified report:
bash experiments/e3_calibration/run_e3.sh
```

See `run_e3.sh`'s header for env-var overrides (`RESIDENCY_PCTS`, `N_PROMPTS`, `MAX_NEW`,
`SKIP_TRANSFER`/`SKIP_E2E`/`SKIP_NF4` to re-run just one sub-step while iterating on it).

## What to look at after running

1. `RESULTS.md`'s provenance table — is every row now `measured_here`? If
   `e2e_offload_runner.py` or `nf4_fidelity.py` needed debugging first (likely, per the
   caveat above), note what was wrong here once fixed, the way E1's design doc records
   its own three real bugs — that record is itself part of what "out-rigors every other
   team," per Experiments.md's own framing of this table.
2. The policy-ordering pass/fail table — does it actually pass at both residency levels?
   If `next-layer-topk` isn't clearly fastest, that's either a bug in the two-pass
   lookahead logic (check whether pass 1 and pass 2 really produced identical
   trajectories — add an assertion comparing them if not already convinced) or a genuine
   and interesting finding that oracle lookahead's benefit is smaller than expected at
   this residency/model combination.
3. `transfer_model_fit.pdf` and the fitted alpha/beta — how do they compare in order of
   magnitude to the CXL alpha/beta Sun et al. (ISCA'23) / Ji et al. (MICRO'24) report?
   That comparison (PCIe-measured vs CXL-literature) is the report's actual point.
4. The NF4 fidelity mean-Jaccard number — is it high enough (e.g. comfortably >0.8) to
   trust that the project's Mixtral-NF4 trace-collection routing decisions are a
   reasonable proxy for what Mixtral-FP16 would have chosen, by analogy from OLMoE's own
   fp16-vs-nf4 agreement?
