# E1 — The MoE Tiering Roofline

Source spec: `Experiments.md` §"E1 — The MoE Tiering Roofline [P0]". This file is the
implementation-specific design note: what we built, why, what it assumes, and how to
run/interpret it. It does not change once written; **results go in `RESULTS.md`, which
is auto-generated by `roofline.py` on every run — don't hand-edit it.**

## Why this experiment, and why first

Every downstream design decision in tierMoE (how much to prefetch, whether precision
fallback is needed, which model class to target, what CXL link width to recommend)
depends on knowing which side of the compute/bandwidth boundary a given configuration
sits on. Experiments.md's own back-of-envelope calculation (§0) showed transfer time
exceeding compute time by 1-2 orders of magnitude for both target models at batch 1 —
meaning prefetch (which only *hides* latency) cannot help until compute time and
transfer time are closer to parity. E1 turns that back-of-envelope observation into a
proper swept model: for every (model, batch, residency, precision, link bandwidth)
combination, compute

```
rho = t_transfer / t_compute
```

`rho < 1`: latency-bound, prefetch can fully hide the fetch behind compute.
`rho >= 1`: bandwidth-bound, only byte reduction (E7's precision-gating) helps.

## Compute-time model: two sources, always labeled

Experiments.md is explicit that E1 should "use a FLOP-based estimate until E3 lands."
E3 (the full hardware calibration ladder: compute + PCIe transfer + e2e offloading +
NF4 fidelity) is a separate, much larger experiment and out of scope here. But since
this **is** running on the target GPU box, we borrow only E3's first sub-step —
`measure_compute.py` times each MoE block's real forward pass (CUDA events) at batch
{1,8,32} — so the roofline can use a **measured** number instead of a guess wherever
that's available. Every number in the output carries an explicit `compute_provenance`
tag:

- `"measured_here"` — from `calib_compute.json` (real GPU timing on this box).
- `"flop_estimate"` — `2*B*k*params_per_expert / (peak_flops * mfu)`, with
  `peak_flops` = RTX 4060 Ti's vendor-spec FP16 tensor peak (22.1 TFLOPS) and
  `mfu = 0.08` (an assumed, documented placeholder for batch-1/8/32 decode MFU —
  **not measured**, and decode-phase MFU is notoriously low and hard to guess).

**This provenance table is the same discipline E3 itself uses** (Experiments.md
explicitly calls that discipline out as something that "will out-rigor every other
team") — applying it a level early, to E1, costs nothing and buys the same defensibility.

Run `measure_compute.py` before `roofline.py` (or let `run_e1.sh` do it) to replace
the flop-estimate with a measurement for whichever models you have GPU time for.

## Assumptions worth knowing before trusting a number

- **`mfu = 0.08`** (`common/model_specs.py::DEFAULT_DECODE_MFU`) is a guess, not a
  citation. It only matters for `flop_estimate` rows; `measured_here` rows ignore it
  entirely. A local dry run (see below) already shows this matters: at `mfu=0.08` the
  flop estimate is pessimistic about compute time, which *overstates* rho (makes
  everything look more bandwidth-bound than it may actually be). Measured compute
  will very likely raise the true MFU-implied compute time in some regimes and lower
  it in others — don't quote a `flop_estimate` rho as a paper number.
- **NF4 byte factor = 4.127/16 ≈ 0.258** (QLoRA, arXiv:2305.14314's double-quant
  bits/param figure), applied uniformly. Real bitsandbytes NF4 overhead varies with
  block size; this is an approximation, same one Experiments.md's own table implies.
- **`E_union(B)` is averaged across layers** into one number per (model, batch) for
  the headline sweep — per-layer detail is retained in `roofline_summary.json` but
  the grid/figures use the cross-layer mean. Real systems would prefetch per-layer;
  this is a reasonable first-order simplification for a roofline, not for E6's
  simulator (which should use the per-layer numbers).
- **Expert byte sizes are architecture-derived** (`ModelSpec.expert_bytes`), not
  hardcoded from the doc's table — `test_expert_bytes_matches_experiments_md_table`
  cross-checks the two agree within 2%, so a future spec change (e.g. a different
  OLMoE checkpoint) can't silently drift from Experiments.md's own numbers without a
  test failing.

## What's already been run (no GPU needed for this part)

`E_union(B)` resampling and the flop-estimate sweep need only the pilot's already-
collected traces (`results/{olmoe,mixtral}/b1/traces.jsonl.zst`) — no model download,
no GPU. This was run locally as an integration test and its output is committed
(`out/`, `RESULTS.md`) as a real first-cut baseline. **What the server run adds:**
`measure_compute.py`'s real GPU timings, which upgrade the `flop_estimate` rows to
`measured_here` and are the main reason to re-run this on the target 2x RTX 4060 Ti
box rather than trusting the committed baseline as final.

## How to run on the server

```bash
# 1. one-time env setup + model download (see ../download_models.sh)
bash experiments/download_models.sh

# 2. optional but recommended: real compute calibration
python3 experiments/e1_roofline/measure_compute.py --model olmoe            # ~1-2 min, loads the real model
python3 experiments/e1_roofline/measure_compute.py --model mixtral --quant nf4   # seconds -- see design note below

# 3. the roofline itself (seconds; no GPU needed once traces + calib exist)
python3 experiments/e1_roofline/roofline.py --models olmoe,mixtral \
  --calib experiments/e1_roofline/out/calib_compute.json
```

Or just run `experiments/run_all_experiments.sh`, which does all of the above (plus
E2) in order. See that script's header for flags (`--skip-download`, `--skip-calib`,
`--n-trials`, etc.).

## Design note: why Mixtral NF4 calibration doesn't load the full model

The first three attempts at `measure_compute.py --model mixtral --quant nf4` all
loaded the real model via `AutoModelForCausalLM.from_pretrained(..., device_map=...,
quantization_config=...)` — the natural-looking approach, and the one this script
originally used. All three hit real, distinct, unrelated bugs in the accelerate/
bitsandbytes multi-device dispatch + CPU/disk-offload machinery:

1. **Fused-experts refactor.** Current transformers (>=4.5x/5.x) refactored
   Mixtral's experts into a fused `MixtralExperts` module holding raw 3D
   `nn.Parameter` tensors instead of per-expert `nn.Linear` layers (the same
   refactor `elp_probe/run_mixtral.sh` already works around for `collect.py`).
   bitsandbytes' `load_in_4bit` only auto-quantizes `nn.Linear` submodules, so
   against the fused module it silently fails to quantize (leaving the ~93GB
   fp16 footprint untouched instead of ~26GB). Fixable by pinning
   `transformers==4.46.3`.
2. **bitsandbytes meta-tensor `.item()` crash during hook attachment.**
   `RuntimeError: Tensor.item() cannot be called on meta tensors`, from
   `bitsandbytes.functional.QuantState.as_dict()` unconditionally calling
   `self.offset.item()` on a still-meta (CPU/disk-offloaded, not yet
   materialized) quant-state tensor, triggered by `accelerate.dispatch_model`
   calling `module.state_dict()` on every module while attaching device
   -alignment hooks. Present even with the transformers pin from (1) applied —
   an independent bug in the accelerate/bitsandbytes combination itself.
3. **`NotImplementedError: Cannot copy out of meta tensor; no data!`** — past
   loading and hook attachment, on the *first real forward pass*. Accelerate's
   `AlignDevicesHook.pre_forward` tries to materialize an offloaded 4-bit
   parameter back onto the GPU just-in-time, and the underlying data was never
   properly retrievable for at least one component of the quant state.

All three are specific to the CPU/disk-offload + multi-device dispatch code path —
none are related to what's actually being measured. That's the key realization:
**per-layer compute time depends only on GEMM shapes, dtype, and quantization
scheme — never on trained weight *values*, and never on loading the real ~93GB
checkpoint.** So `measure_compute.py`'s `--quant nf4` path no longer loads the real
model at all. It builds one `StandaloneMoEBlock` (router + experts, SwiGLU FFN)
directly on a single GPU with random weights, using `bitsandbytes.nn.Linear4bit` in
its standard, well-supported single-device usage pattern — construct, then
`.to(device)`, which performs real NF4 quantization with **no accelerate dispatch
hooks, no CPU/disk offload, and no multi-device planning involved at all** (the same
pattern PEFT/LoRA use to build quantized base layers). Mixtral's decoder layers are
architecturally identical across depth (no per-layer size variation), so this one
block's timing is reported for every layer index — not an approximation of the
per-layer numbers, it *is* the per-layer number, for all 32 layers.

Consequences worth knowing:
- This calibration no longer needs `transformers==4.46.3` pinned, or Mixtral's
  weights downloaded at all (though you'll still want the download for anything
  that DOES need real routing behavior, like trace collection via `collect.py`).
  Both `--cpu-offload-gb` and `--gpu-mem-frac` were removed from the CLI — they no
  longer apply.
- **The transformers pin is still required for `collect.py`/`run_mixtral.sh`**
  (real trace collection needs real weights and real routing) — that's issue (1)
  above, unrelated to this calibration script now. Don't remove that pin from
  `run_mixtral.sh`.
- Runs in seconds instead of the ~18 minutes a full Mixtral NF4 checkpoint load
  took, and is hardware-agnostic (needs only ~1GB of VRAM for the block itself,
  works identically on a 24GB single GPU or a multi-GPU pool).

## Exit criteria (Experiments.md's own wording)

> "You can state, in one sentence with numbers, the condition under which
> router-guided prefetch is worth anything."

`roofline.headline_sentences()` auto-derives exactly this sentence per (model,
precision) from the swept grid — see the "Headline" section of the auto-generated
`RESULTS.md`. It also handles the doc's own expected failure mode honestly: if no
point in the swept grid reaches ρ<1, it says so explicitly ("byte reduction, not
prefetch alone, is required here") rather than silently reporting a misleading "best"
row.

## What to look at after running

1. `RESULTS.md`'s headline sentences — do they match the doc's expected shape
   ("fine-grained MoE, expert ≤~30MB, at batch≥8, ≥50% residency, ≥64GB/s")?
2. `out/figures/roofline_{model}_{precision}.pdf` — does the ρ=1 boundary (black
   contour line) separate OLMoE and Mixtral the way §0's reframing predicts? Are the
   pilot's real Coverage@C points (green stars) on the hideable or bandwidth-bound
   side?
3. `out/provisioning_table.csv` — the continuous minimum-bandwidth numbers, for the
   report's provisioning table.
4. Compare `flop_estimate` vs `measured_here` rows once calibration has run — any
   regime where the conclusion flips is worth a sentence in the report's limitations
   section.
