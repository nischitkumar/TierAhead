# E5 — Lookahead Depth and Pipelined Prefetch

Source spec: `Experiments.md` §"E5 — Lookahead depth and pipelined prefetch [P1]".
Design note: what's implemented, what it assumes, how to run/interpret it. **Results go
in `RESULTS.md`, auto-generated by `lookahead.py` on every run — don't hand-edit it.**

**Runs on a laptop, not (only) the GPU server** — "Effort 10h (reuses E4 machinery)" per
Experiments.md, and that's literally true here: this experiment imports `features.py` and
`mlp.py` straight from `../e4_predictor/` rather than reimplementing anything. Full sweep
(both models, d ∈ {1,2,4,8}, direct + chained, feasible-fetch-size, queue sim) ran on this
machine's CPU (no CUDA) in about 5.5 minutes.

## Why this experiment exists

One layer of lookahead buys one layer of compute time to hide a fetch behind. E1 already
showed that window is 50-100x too small for coarse experts (Mixtral). The only lever left
is deeper lookahead — predict layer l+d and start fetching d layers early — but two things
work against you as d grows: prediction accuracy naturally decays the further out you
predict, and *naively chaining* a one-step predictor d times (feeding its own uncertain
output back in as the next hop's "observation") compounds that decay on top. This
experiment measures both curves separately so the report can say which effect actually
dominates, not just that recall drops with depth.

## What's actually implemented

| Experiments.md E5 step | File / function | Notes |
|---|---|---|
| 1. Direct predictors per d, not chained; chained measured as comparison | `lookahead.py::direct_recall_for_depth`, `chained.py` | Direct: one `ids_gate_entropy` MLP per (layer, d), same machinery as E4. Chained: one `ids`-only d=1 MLP per layer, composed d times — see "Why chaining can only use the 'ids' variant" below. |
| 2. Recall@m vs d, nonresident | Both of the above, using E4's `feat.resident_mask` / `mlpmod.topm_hits_and_total` directly | Same 25% nonresident definition as E4 and the pilot, for apples-to-apples comparison across all three. |
| 3. Feasible-fetch-size curve | `feasible_fetch.py` | Reuses E1's `roofline.get_t_compute_ms` — compute-time estimation lives in exactly one place in this codebase. `bytes_fetchable = d * t_layer_ms * BW`, overlaid against each model's real per-expert byte size. |
| 4. Prefetch queue / pipelining simulation | `queue_sim.py` | Closed-form (not Monte Carlo) — see the module docstring for the exact derivation of why deterministic arrivals + deterministic service admit an exact solution. |

## Why chaining can only use the "ids" variant

The direct predictors use `ids_gate_entropy` (E4's best-performing features: which
experts fired, how confidently, how uncertain the router was) because all of that is
*real*, observed information at layer l. Chaining can't do the same at intermediate hops:
after the first hop, the "layer" you're predicting from is a *predicted* state that never
actually executed — there's no real router logit to compute a gate weight or entropy
from. The only thing a chained predictor can legitimately feed forward is its own belief
about which experts would fire (a k-hot vector), because that's the only quantity that
has a well-defined value for a hypothetical layer. So the chained baseline necessarily
uses the `ids`-only variant at every hop, and the direct baseline gets the richer
features — this makes the comparison slightly favor direct beyond just "one hop vs many,"
which is honest and worth stating rather than papering over: chaining is disadvantaged
both by compounding uncertainty *and* by losing access to gate/entropy features it can't
legitimately reconstruct. Both are real, structural reasons a real system would prefer
direct multi-step predictors over chaining, so reporting them together isn't unfair to
chaining — it's the actual shape of the tradeoff.

## Result found (both models, run on this machine)

The direct-vs-chained recall gap **widens monotonically with depth** for both models —
exactly Experiments.md's own prediction ("chaining compounds error"):

| Model | d=1 gap | d=2 gap | d=4 gap | d=8 gap |
|---|---|---|---|---|
| olmoe | +0.019 | +0.076 | +0.117 | +0.170 |
| mixtral | +0.008 | +0.053 | +0.091 | +0.100 |

At d=1 the two are nearly identical (as they should be — one hop is one hop regardless of
label), and the gap grows roughly linearly with d from there. This is a clean, expected,
reportable result — see `RESULTS.md` for the full recall numbers and figures.

## Honest caveats

- **`t_compute` is `flop_estimate`, not `measured_here`**, since no GPU calibration file
  exists on this machine. `RESULTS.md`'s feasible-fetch-size section says so explicitly
  and links to running E1's/E3's `measure_compute.py` first. Pass `--calib <path>` (or
  `CALIB=<path> bash run_e5.sh`) once that file exists on the server.
- **Recall threshold for "max useful depth" is 0.60**, matching the pilot's own
  `STRONG_GO` verdict threshold (`Pilot.md`/`elp_probe/src/analyze.py::verdict`) — but the
  pilot's own threshold was checked at **m=2k**, while this experiment's recall numbers
  are at **m=k** (matching E4's own ablation granularity). Neither model clears 0.6 at
  m=k for any tested depth on this run — expected given the pilot's own m=k numbers were
  already well under 0.6, not a sign of a broken predictor. Don't directly compare this
  "0.6 at m=k" result to the pilot's "0.6 at m=2k" verdict without accounting for that.
- **Queue simulation is closed-form/deterministic**, not an event-driven Monte Carlo
  (unlike E8's link simulator) — deliberately, because deterministic arrivals and
  deterministic service admit an exact solution (see `queue_sim.py`'s docstring), so
  simulating it stochastically would only add noise, not accuracy.
- **Feasible-fetch-size and queue-sim both use `--fetch-batch 1`** (single-request
  decode) by default — the "one layer of lookahead buys one layer of compute time"
  framing is inherently a per-request notion; batching's effect on this is E2's subject,
  not E5's.

## A real import bug caught while building this (recorded, not just fixed silently)

The first full run trained correctly and printed sensible recall numbers for both models,
then crashed at the very last step (`KeyError: 'compute_provenance'`) while rendering
`RESULTS.md` — because `from render_results_md import render` resolved to **E1's**
`render_results_md.py`, not this directory's own. Root cause: this script's `sys.path`
also includes `e1_roofline/` (for `roofline.get_t_compute_ms`) and `e4_predictor/` (for
`features`/`mlp`), and each of those directories has its own same-named
`render_results_md.py` — whichever got inserted onto `sys.path` last wins an unqualified
`import render_results_md`, and it wasn't this file's own directory. E1 and E2 already
avoid this exact trap by re-inserting their own directory onto the front of `sys.path`
*immediately before* their own equivalent import, rather than relying on an insert from
the top of the file to still be in front after several other directories get added later
— this file didn't do that second insert, so it inherited the bug. Fixed by adding the
same re-insert immediately before the `import render_results_md` line, with a comment
explaining why it's needed (the fix is easy to "clean up" by someone who doesn't know why
it's there, so the reasoning is in the code, not just this doc).

## Exit criteria (Experiments.md's own wording)

> "A stated maximum useful depth per model, plus the resulting maximum expert size."

`RESULTS.md`'s "Exit criteria" section states this per model automatically
(`feasible_fetch.max_useful_depth`) — including the honest case where no swept depth
clears the threshold, which is what actually happened on this run (see caveats above for
why that's expected given the m=k vs m=2k mismatch, not a red flag).

## What to look at after running

1. Does the direct-vs-chained gap in `RESULTS.md` widen with d for both models, and by
   roughly how much — is it big enough to matter for a real system's choice between
   "train one predictor per depth" vs "chain a single predictor" (much more code/GPU
   memory for the former)?
2. Cross-reference the feasible-fetch-size table against E1's provisioning table: at
   whatever depth/bandwidth combination is "affordable," does the corresponding recall
   number (from the recall-vs-depth table) actually deliver useful prefetch accuracy?
3. The queue-sim table's `rho` column — is it >>1 at the swept bandwidths (meaning expert
   traffic alone already can't keep up, matching E1's own bandwidth-bound finding at
   batch=1), or closer to 1 (meaning queue depth would actually matter)? On this run rho
   was 14-110x at batch=1 across the whole bandwidth grid — consistent with E1's finding
   that batch=1 decode is deep in the bandwidth-bound regime for both models.
