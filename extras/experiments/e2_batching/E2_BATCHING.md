# E2 — Batching Sweet Spot: Locality Erosion vs Arithmetic Intensity

Source spec: `Experiments.md` §"E2 — Batching sweet spot [P1]". Implementation-specific
design note. **Results go in `RESULTS.md`, auto-generated by `batching_sweep.py` on
every run — don't hand-edit it.**

## Why this experiment

E1 says batching helps hide latency (more compute per byte per token). The pilot's
own batch-8 erosion check said batching hurts locality (OLMoE's touched-expert
fraction widened from 12.5% at batch 1 to 47% at batch 8). These pull in opposite
directions, so there's an optimum batch size, and Experiments.md's hypothesis is that
its position depends on expert granularity — the same architectural knob that drove
the pilot's skew-inversion finding (fine-grained MoEs are *more* skewed than coarse
ones, backwards from the naive intuition). This experiment finds that optimum, B*,
for both models and checks whether the claim holds up quantitatively.

## What's actually implemented

| Experiments.md step | File | Notes |
|---|---|---|
| 1. `E_union(B)` for B∈{1,2,4,8,16,32,64} via resampling | `common/eunion.py` (shared with E1) | Same resampling machinery E1 uses; batch grid is finer here (`BATCH_GRID_E2`). |
| 2. bytes/token = `E_union(B)*size*(1-r)/B` | `batching_sweep.bytes_per_token` | The key amortization quantity. |
| 3. Combine with E1's compute model → ρ(B), find B* under a TPOT SLO | `batching_sweep.find_b_star` | See "Throughput vs latency" below — this is the part that had a real bug during development. |
| 4. Predictor recall for *batched* targets (new metric) | `batching_sweep.batched_recall` | Reuses `elp_probe/src/analyze.py`'s `build_transition_tables` — same fitted predictor as the pilot, not a new one. |

## Throughput vs latency — a real modeling bug found while testing this, fixed

An earlier version of `find_b_star` computed `total_tpot_ms = n_layers * per_token_time_ms`.
That's wrong: `per_token_time_ms` is *already* divided by batch (it's a throughput
metric — bytes/compute amortized across every token in the batch). The actual
per-request latency for one decode step — the thing a p99 TPOT SLO should constrain —
is the **undivided** batch-step time, because every request in a batch waits for the
same layer forward pass to finish, regardless of how many other requests are riding
along. Using the divided quantity made `total_tpot` monotonically *decrease* with
batch, so an SLO could never bind and B* was always the largest grid point — silently
hiding the exact tradeoff this experiment exists to find.

Fixed in `batch_step_components_ms` / `find_b_star` (see that function's docstring)
and locked in by `test_total_tpot_is_undivided_batch_step_time_not_per_token_time_times_n_layers`
in `tests/test_batching.py`, which constructs a compute-bound case where the bug and
the fix produce numerically distinguishable answers. **Concretely:** with the fix, at
r=25%/bw=64GB/s/fp16/SLO=100ms, OLMoE's B* comes out to 8 (a genuine interior optimum
— total TPOT crosses 100ms between batch 8 and 16), while Mixtral's total TPOT never
gets under 100ms at any batch in the grid at that operating point (its expert is 28x
bigger, so even batch-64 amortized transfer still dominates). See the committed
`RESULTS.md` for the exact numbers.

**`--slo-ms` is a configurable assumption, not a spec-given number** — Experiments.md
doesn't pin one. The default in `run_e2.sh` (100ms) is a reasonable interactive-serving
p99-per-decode-step placeholder; change it and re-run if you have a different target.
Without an SLO the "sweet spot" is undefined — larger batch always wins on throughput
alone, so `find_b_star` will just return the largest grid point (this is itself a real
and correct result, not a bug: it says the erosion cost only bites once you have an
actual latency budget, which matches how E6's later SLO-constrained sweep will use it).

## The batched-recall metric: another subtlety found while testing

Naively, raw `recall_overall` for the batched-union target metric can *rise* with
batch even for a **completely unlearnable** (random) transition table. This isn't a
bug — it's because each of the B rows in a batch contributes its own top-m candidate
set, so the aggregate candidate pool (`pred_union`) mechanically grows with B,
independent of prediction quality. A bigger net catches more fish even with zero
skill. Two consequences, both handled in the code:

1. **Every result now reports `baseline_random_batched`** — the batch-scaled chance
   floor (`E[|union of B iid uniform m-subsets|] / n_experts`, via
   `common/eunion.py::analytic_e_union_uniform`), the batch analogue of the pilot's
   `baseline_random = m/n_experts`. Compare `lift_over_random_batched = recall_overall
   - baseline_random_batched` across batch sizes, not raw recall — this is what the
   predictor is actually contributing.
2. **When `n_experts` is small relative to batch, both `pred_union` and `actual_union`
   saturate toward the full expert set and recall trivially → 1 regardless of skill.**
   This is the exact "m=4k is degenerate for Mixtral because m==n_experts" artifact
   `PILOT_FINDINGS.md` §5 already flagged for the single-token metric, generalized to
   batch: Mixtral (8 experts/layer) will saturate this way at much smaller batch than
   OLMoE (64 experts/layer). Watch for this specifically in Mixtral's batch≥8 rows —
   high recall there is likely saturation, not signal. Both behaviors are unit-tested
   (`test_batched_recall_has_near_zero_lift_for_a_noisy_transition_at_any_batch`,
   `test_batched_recall_saturates_when_batch_approaches_n_experts`).

## Claim check

Experiments.md's exit criteria: *"the claim 'fine-grained MoEs have a wide viable
batch window, coarse MoEs have none' is either confirmed with numbers or refuted."*
`_render_claim()` auto-derives this by counting, at the analysis's fixed (r, bw,
precision), how many of the 7 swept batch sizes land in the latency-hideable (ρ<1)
regime for each model, ranked by `n_experts`. **This is sensitive to the operating
point** — a local sensitivity probe during development found the verdict flips
between INCONCLUSIVE (both 0/7 at r=25%,bw=64GB/s) and REFUTED (Mixtral wider window
than OLMoE at r=50%,bw=128GB/s) depending on where you look, under the flop-estimate
compute model. **Don't quote a single run's verdict without checking a couple of
nearby operating points**, and re-check once `measure_compute.py`'s real numbers
replace the flop estimate — the crude `mfu=0.08` guess is doing real work in these
borderline cases.

## How to run on the server

```bash
bash experiments/download_models.sh                       # once
bash experiments/e1_roofline/run_e1.sh                     # calibration + roofline (pins
                                                            # transformers==4.46.3 for Mixtral
                                                            # NF4 automatically -- see
                                                            # E1_ROOFLINE.md's "Known issue")

python3 experiments/e2_batching/batching_sweep.py --models olmoe,mixtral \
  --calib experiments/e1_roofline/out/calib_compute.json \
  --residency-pct 25 --bw-gbps 64 --precision fp16 --slo-ms 100
```

The recall step (E2 step 4) is the slow part (~200 trials × 7 batches × ~15-31 layers
per model); pass `--skip-recall` for a fast core-only run, or `--recall-n-trials 50`
to trade precision for speed. On this repo's already-collected traces (no GPU/network
needed), the full default run (both models, recall included) took under a minute.

## What's already been run

Like E1, this experiment needs only the pilot's b1 traces — no GPU or model download.
It was run locally as an integration test at default settings (`--slo-ms 100`,
`flop_estimate` compute) and the output is committed as a real first-cut baseline.
Re-run on the server with `measure_compute.py`'s calibration to get `measured_here`
compute numbers, and consider sweeping `--residency-pct`/`--bw-gbps` given the
sensitivity noted above before treating the claim-check verdict as final.
